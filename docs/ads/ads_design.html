Status: Proposed Design Doc AdMob · Compose · Consent

Display Ads — Free Tier

Engineering design for in-list display ads. Companion to the PRD: the pure placement core, the app-session cap and the foreground observer it needs, the entitlement gate, how three list surfaces with two different scroll mechanics take ad rows, the per-host SDK seam (including why iOS needs a Swift bridge rather than cinterop), and a phased build roadmap.

Implementation Status P1–P8 shipped (#378–#385): placement core, the session cap, the tier gate, Android AdMob end to end, consent (UMP on both platforms — the iOS CMP added mid-P8; ATT deliberately dropped, see §8), and the iOS ad view via the Swift bridge, with real Android and iOS AdMob app ids and per-surface ad units on both platforms. Revised post-P7: the CMP dialog moved from a lazy AdSlot-triggered call to a one-time AuthFlow onboarding step with its own priming explainer, covering new and returning users alike — see the P7 roadmap entry. P9 (store disclosures, flipping isAdsSupported for GA) and P10 (phase 2 web ads) have not started. The PRD's decisions D1–D9 are settled inputs here and are not re-litigated; where this doc contradicts an assumption the PRD made about existing infrastructure, §3 and §5 say so explicitly.

1. Overview & Principles

Four commitments shape the design:

  • Placement is pure, testable Kotlin. Cadence, the empty-list rule, slot positions, the session cap and the per-tier slot format are decided by code that imports no Compose and no ad SDK. The PRD's §6.6 test matrix becomes unit tests over withAdSlots(), not screenshot tests.
  • The ad product is behind one seam. Only feature/ads/viewing touches an SDK, through a single expect/actual AdView. That is what lets AdMob serve mobile now and an Ad Manager tag serve web in phase 2 (PRD §8.2) without reopening this document.
  • Default-OFF, the mirror of the other gates. isSubscriptionSupported is default-open (no paywall ⇒ everything available). Ads invert it: no subscription support, or no ads support, ⇒ no ads. A build where Pro cannot be bought must never show ads a pilot cannot remove.
  • The record always wins. Every guardrail G1–G10 that can be made structural is made structural — collapsed-by-default slots, fixed creative sizes, neutral tokens — rather than left to a reviewer to catch.
Three findings that change the plan Tracing the PRD against the codebase turned up three assumptions that do not hold. Each has a section below and a line in the roadmap, because each is real work the PRD treated as free: (A) the three surfaces use two different list mechanics, and only one is lazy (§5); (B) there is no app-session or foreground-observer concept in the codebase to hang the 5-per-session cap on (§4); (C) iOS links SDKs via SPM in the Swift app, so iosMain cannot reference GADBannerView at all (§7.2).

3. The Placement Core

Everything normative in PRD §6 lives in feature/ads/model as pure functions over lists.

sealed interface ListRow<out T> {
  data class Item<T>(val value: T) : ListRow<T>
  /** 0-based, stable for a given list size. The Lazy list key where one exists. */
  data class Ad(val slotIndex: Int) : ListRow<Nothing>
}

enum class AdSurface { SQUAWKS, TASKS, LOGS }        // the analytics `surface` param
enum class AdSlotFormat { SINGLE, TWO_UP }           // resolved from tier + headroom
enum class AdUnitSize { BANNER, LARGE_BANNER }       // PRD D7 / §7.2

fun <T> withAdSlots(items: List<T>, interval: Int = 10): List<ListRow<T>>

Callers wrap only when ads are enabled; when disabled they render items directly, so the ad-free path allocates nothing (PRD §6.3).

3.1 Slot positions are pure; fills are not

This split is the single most important idea in the design, and PRD §6.6 depends on it being respected:

Decided byDepends onTestable as
Slot positionswithAdSlots()rendered item count onlypure unit test, PRD §6.6 table
Slot formatAdSlotFormat.of(tier, headroom)layout tier + remaining cappure unit test, per tier
Which slots fillAdSessionCountersession state, scroll history, networkcounter unit tests + manual

At a cadence of 10 with a cap of 5, a 100-item list produces ten slots of which at most five ever fill. A reviewer reading only the §6.6 table would reasonably implement ten fills; the doc says so and so does this one.

3.2 Grouped and toggled lists

Compliance's status groups share one continuous counter across the whole scroll, and a slot landing on a group boundary renders at the end of the preceding group (G1 — never between a header and its first card). The caller flattens to a single list of headers-and-cards and calls withAdSlotsGrouped(entries, isHeader = …), which counts only non-header entries toward the cadence.

Simplified during P2: no repair pass is needed This section originally specified a second coalesceAcrossHeaders() function to shift any ad that landed against a header. Implementing it showed the pass is unnecessary, because ads are only ever emitted immediately after a record. That makes [header, ad, …] unconstructible, so G1 holds by construction rather than by repair — and G2 (never the first card) holds for the same reason, since row 0 is always an item. A boundary slot naturally lands as […lastRecordOfGroupA, ad, headerOfGroupB…], which is exactly what §6.5 asks for. One function instead of two, and one fewer place for the invariant to be broken later.

Squawks' Open/Closed toggle is two independent lists with independent counters — falls out for free, since each sub-view calls withAdSlots() on its own filtered list.

4. The Session Cap

4.1 AdSessionCounter

An app-scoped Koin single — the cap is global across surfaces, so exactly one instance may exist. It is the only thing that decides whether a composed slot may request an ad.

class AdSessionCounter(clock: Clock, foreground: AppForegroundObserver) {
  /** Units displayed this session, 0..5. */
  val displayed: StateFlow<Int>
  val headroom: Int get() = CAP - displayed.value

  /** Reserve n units (1 for SINGLE, 2 for TWO_UP). Returns what was granted: 0, 1 or 2. */
  fun reserve(units: Int): Int

  companion object { const val CAP = 5 }
}

reserve() returning a partial grant is what implements PRD §7.1's "near the cap" rule without a special case at each call site: a TWO_UP slot asking for 2 with one unit of headroom gets 1, and AdSlotFormat resolution then centres the single unit exactly as the MEDIUM case.

Fill caching (N8). A slot's grant is remembered per slotIndex for the lifetime of the screen, so scrolling past the same ad twice neither re-requests nor double-counts. Held in a remember-scoped map keyed by surface — deliberately not in the counter, which must stay screen-agnostic.

4.2 The missing piece: there is no app session today Finding B

PRD §6.7 defines the session boundary as "cold start, or foregrounding after ≥ 30 minutes in the background — the same convention as the analytics session." No such convention exists in the codebase. Specifically:

  • AnalyticsManager (core/analytics) exposes only logScreenView, logEvent and setAnalyticsCollectionEnabled. Firebase maintains its own session internally and does not surface a session id or boundary to the app.
  • There is no app-level foreground/background observer. The closest thing is LifecycleResumeEffect in AircraftSectionContent (added for the #373 due-status recompute) — that is screen-scoped, fires on tab switches, and would reset the ad cap far too often.

So the design adds one, in a new core/lifecycle module. androidx.lifecycle.compose is already a dependency and LifecycleResumeEffect already works on all three hosts (the #373 comment confirms: UIKit foreground on iOS, document.visibilitychange on web), so the primitive exists — what is missing is an app-scoped owner of it.

Why its own module, and not core/ui

Because its consumer may not depend on UI. AdSessionCounter lives in feature/ads/datamanager, and AGENTS.md is explicit that datamanager and model never depend on UI. A UI-module observer would force precisely that violation, in the one place it would be least visible — a transitive dependency rather than an import someone reviews. core/lifecycle also reads correctly to the next person: an app-session signal is not a UI concern, and future consumers (analytics, sync backoff) are not UI either.

The consequence is a two-part split. LifecycleResumeEffect is a Compose API, so a non-UI module cannot use it. The observer is therefore a pure state machine, and something in the UI layer pumps it:

// core/lifecycle — commonMain, no Compose, no expect/actual
class AppForegroundObserver(private val clock: Clock) {
  /** Emits at cold start and whenever the app foregrounds after ≥ [threshold] backgrounded. */
  val sessionStarts: Flow<Unit>
  fun onEnterForeground()
  fun onEnterBackground()
  companion object { val THRESHOLD = 30.minutes }
}

// feature/shell — the driver: the only Compose-aware part, ~5 lines at the shell root
LifecycleResumeEffect(Unit) {
  observer.onEnterForeground()
  onPauseOrDispose { observer.onEnterBackground() }
}

This split is a win rather than a tax: the state machine is unit-testable with a fake clock and no Compose test harness, and the host-specific behaviour stays in the one primitive that already handles all three platforms. The alternative — per-host expect/actual actuals over ProcessLifecycleOwner, NSNotificationCenter and visibilitychange — is three times the code and three times the platform surface for the same signal.

Scope call This is genuinely useful beyond ads — a real app-session signal is what the analytics design has wanted for its click/timing taxonomy, and #373's resume recompute is a screen-scoped stand-in for it. It is scoped here as minimum viable for the cap (one flow, one threshold) rather than as an analytics session-id feature, so ads are not blocked on a larger discussion. A dedicated module is what keeps the next consumer from having to dig it out of an ads feature.

Deliberately not persisted. The counter is in-memory. A process death resets it, which can over-count across a crash-restart — accepted for the same reason PRD §6.7 accepts the memory-pressure over-count: bounded, rare, and cheaper than a disk write on every impression.

5. Surfaces — Two List Mechanics Finding A

The PRD describes all three surfaces in one voice and refers throughout to "the Lazy list key." In fact only the logs list is lazy, and the consequences are large enough that the two cases need different handling.

SurfaceContainerLazy?Consequence for ads
Squawks
SquawkTab		 AdaptiveCardList No Plain Column/Row inside an outer verticalScroll. Every card composes; nothing recycles; there are no keys.
Tasks
ComplianceSection		 AdaptiveCardList No Same.
Logs
MaintenanceLogListContent		 LazyColumn, key = { it.id } Yes Slots compose as they scroll into view; Ad(slotIndex) is a real key; off-screen views can be released.

5.1 What this means

  • N5 ("slots far off-screen release their ad view") is free on logs and impossible on squawks/tasks. In a non-lazy list every composed ad view stays alive. This is not a blocker — the 5-unit cap bounds live views to five by construction, which is exactly the "small bounded number" N5 asks for. But the cap is now doing memory work, not just UX work, and lowering it later has a memory benefit while raising it has a memory cost. Recorded here so a future cap change is not made on UX grounds alone.
  • Cap consumption differs by surface. Non-lazy: all slots compose at once, so the first five in list order win, deterministically. Lazy: only visible slots compose, so the cap is consumed as the pilot scrolls. Both are correct and neither is surprising in use, but a test asserting "slot 7 never fills" holds only on the non-lazy surfaces.
  • Stable keys matter only on logs. Where they matter they are load-bearing: Ad(slotIndex) must not change identity as items load in, or Compose tears the slot down and re-requests, burning cap.

5.2 AdaptiveCardList needs a spanning row API change

Today the signature admits no ads at all:

@Composable fun <T> AdaptiveCardList(
  items: List<T>, columns: Int, modifier: Modifier, spacing: Dp,
  itemContent: @Composable (T) -> Unit,
)   // chunks items into rows of `columns`; every cell weight(1f)

PRD §6.5 requires the ad to occupy a full-width row spanning all columns, with cadence counted per item rather than per row. Chunking a List<ListRow<T>> through the existing function would place an ad in a single grid cell — the one thing §6.5 forbids. Two options considered:

OptionShapeVerdict
Each surface composes its own rowsCallers stop using AdaptiveCardList and hand-roll the grid with ad rowsRejected — duplicates the chunking and short-row padding logic in three places, and diverges over time.
Teach the component about spansOverload taking rows: List<ListRow<T>>, chunking only Items and emitting each Ad as a full-width row between chunksChosen. One place owns grid mechanics; the ads knowledge is one when branch. core/ui/adaptive already depends on nothing feature-specific, and ListRow lives in feature/ads/model — so the overload takes a generic sealed shape or a simple isSpanning: (T) -> Boolean predicate to avoid a core→feature dependency.

The predicate form is preferred on layering grounds: core/ui/adaptive must not import feature/ads/model.

5.3 Logs: the scroll-target bug the PRD flags as F8

Concrete and worth quoting, because it is a correctness issue rather than a cosmetic one. MaintenanceLogListContent pins a target log by item index:

snapshotFlow { currentLogs }.collect { logs ->
  val index = logs.indexOfFirst { it.id == scrollToLogId }
  if (index >= 0) logListState.scrollToItem(index)     // ← item index, not display index
}

With ads interleaved, logs.indexOfFirst and the LazyColumn's index diverge by the number of ads above the target — so a pilot tapping "go to this log" lands on the wrong entry, and the error grows down the list. The fix is to resolve against the display list: rows.indexOfFirst { it is ListRow.Item && it.value.id == scrollToLogId }. A regression test pins it with ads on and off.

5.4 The wide log table

MaintenanceLogTable (MEDIUM+) renders ads as a full-width band between rows (PRD D3/F16), matching the table's horizontal insets but adopting none of its column rules, zebra striping or row height. Implementation note: the band is emitted by the same AdSlot() composable as the card surfaces, wrapped in a container that supplies the table's insets — no table-specific ad code.

6. The Gate

SubscriptionManager gains one method, alongside the existing canUploadAttachments() / canEmailExports() / canHostShare() / aircraftLimit():

/** True only for the free tier, on a build/platform where ads are supported. Default-OFF. */
fun showsAds(): Flow<Boolean>

The implementation is the inverse of the existing gate() helper, and the asymmetry is the whole point:

override fun showsAds(): Flow<Boolean> =
  // Default-CLOSED, unlike gate()/aircraftLimit(): no ads unless we can also sell removal.
  if (!appCapability.isAdsSupported || !appCapability.isSubscriptionSupported) {
    flowOf(false)
  } else {
    status().map { it < Subscription.Status.STATUS_PRO }
  }

Reading the status enum rather than a boolean means any future paid tier is ad-free automatically. Being a Flow off the same entitlement stream makes PRD F5 fall out: a purchase resolves, showsAds() emits false, in-flight slots collapse without a restart; on expiry they return.

AppCapability.isAdsSupported follows isAircraftSharingSupported/isSubscriptionSupported: a build-time flag in each host's createAppCapability actual — on in dev and dogfood, off in the shipping release until GA, and false on the JS host for all of v1. Its KDoc must state the inversion explicitly, since every neighbouring flag means the opposite: off means no ads, not ads-for-everyone.

Guests and shared aircraft need no special code. A guest is on the free tier and sees ads under the same rules — and sees none in practice at first, because their lists are empty (G3). Ads follow the viewer's own entitlement, so a free mechanic viewing a Pro owner's shared aircraft sees ads; nothing consults the host's tier.

7. The Platform Seam

One expect declaration, three actuals. AdSlot() in commonMain owns the label, the band layout, the upsell link, the collapse-when-unfilled behaviour and the analytics calls; AdView() owns nothing but the creative.

// feature/ads/viewing/commonMain

7.1 Android

Straightforward: add com.google.android.gms:play-services-ads to gradle/libs.versions.toml and to feature/ads/viewing's androidMain only. The actual is an AndroidView wrapping AdView with a fixed AdSize.BANNER, an AdListener mapped onto the three callbacks, and MobileAds.initialize() called lazily on first showsAds() == true (P6) rather than at app start. The manifest needs the AdMob app id; a placeholder for dev keeps release keys out of the repo.

7.2 iOS — SPM means a Swift bridge, not cinterop Finding C

The PRD sketch says "iosMain: GADBannerView + ATT/UMP". That is not reachable as written. iosApp has no Podfile: dependencies come in as XCRemoteSwiftPackageReference (Swift Package Manager) — Firebase and GoogleSignIn both. Without the Kotlin CocoaPods plugin there is no cinterop, so iosMain cannot see GADBannerView at all.

The repo already has the answer, and it is a pattern rather than a workaround. MainViewController.kt exposes:

/** …`FirebaseAppCheck` is linked there [Swift], not in Kotlin/Native. */
fun installAppCheckTokenProvider(provider: (onToken: (String?) -> Unit) -> Unit) {
  IosAppCheckBridge.install(provider)
}

Ads follow the same shape exactly:

  1. Add googleads-mobile-sdk-ios as an SPM package on the iosApp target.
  2. Swift owns a small factory that builds a configured GADBannerView (unit id, size, delegate → callbacks) and returns it as a UIView.
  3. MainEntry.installAdViewFactory { … } hands that factory to IosAdViewBridge at startup, alongside the existing Google Sign-In and App Check installs.
  4. The iosMain actual is a UIKitView over the bridge-supplied view. If no factory was installed the actual renders nothing — the same collapse path as an unfilled slot, so a misconfigured build degrades to ad-free rather than crashing.
Build-verification caveat iOS is not built on CI, and #374 shipped its Swift branch explicitly "not compile-verified" because the Kotlin framework build phase fails before Swift compiles. The ads Swift bridge inherits that exposure: it must be built and run on a simulator locally before the iOS flag is flipped, and the roadmap makes that an explicit gate rather than an assumption.

7.3 Web

v1: the jsMain actual renders nothing. It exists so the shared placement code compiles and so phase 2 is a drop-in (PRD W5). Phase 2 replaces it with a lazily-injected Ad Manager GPT tag; nothing else in this design changes.

8. Consent & Privacy

AdConsentManager in feature/ads/datamanager, expect/actual, no-op on JS in v1:

interface AdConsentManager {
  /** Resolves consent before the first ad request. Never throws; failure ⇒ non-personalized. */
  suspend fun ensureConsent(): AdConsentState   // PERSONALIZED | NON_PERSONALIZED | DENIED
  /** Re-presents the CMP form from Settings, where the CMP requires it (P4). */
  suspend fun presentPrivacyOptions()
}
  • Ordering is a hard requirement. No ad request is made before consent resolves (P2). The gate chain is showsAds() → consent → MobileAds.initialize() → first request, and every step is lazy for a Pro user: their app never starts an ad SDK and never calls a CMP (P6/N6). Consent itself is no longer only lazy, by design. AdConsentManager.ensureConsent() split into isConsentRequired() (background requestConsentInfoUpdate, no UI) and presentConsentForm() (the actual dialog) so AuthFlow can resolve the background check right after onboarding, for every free-tier pilot in a region requiring one, and put a priming explanation in front of the real CMP dialog before showing it — rather than let the dialog interrupt whoever happens to open an ad-eligible list first. AdSlot's lazy ensureConsent() call (= presentConsentForm()) remains as a fallback for whatever onboarding didn't cover.
  • No ATT prompt (P3, revised). iOS deliberately never requests App Tracking Transparency. Apple only requires it for apps that read IDFA / track across other companies' apps and sites (Review Guideline 5.1.2) — it is not required to serve ads at all, and stacking it after the CMP would ask an EEA/UK pilot two consent questions back to back for what reads as the same thing. A declined ATT prompt already collapsed to NON_PERSONALIZED here (identical to a partial CMP decline), so omitting it loses no ad-serving capability, only the IDFA-targeted tier. iOS therefore never resolves to PERSONALIZED; only Android does, via UMP consent alone.
  • No logbook data, structurally. AdView's signature takes a size and three callbacks — there is no parameter through which a tail number, squawk text or uid could reach an ad request even by accident (P1). The absence of a targeting parameter is the enforcement mechanism.
  • Store disclosures (Play Data Safety, App Store privacy labels) are updated before the first release with ads enabled (P5) — a release-checklist item in the roadmap, not code.

Through the existing AnalyticsManager.logEvent(name, params: Map<String, String>). Note the params map is String-valued, so numeric fields are stringified at the call site; names must be GA4-legal (snake_case, ≤40 chars) as the interface KDoc warns, and are passed through unvalidated.

Expect the impressions-per-session distribution to pin at 5 for engaged users (PRD §12): at interval 10 the cap binds early, so a pinned distribution is the design working, not a bug.

10. DI, Developer Options & Wiring

  • adsModule registered in core/di/CommonAppModules.kt — the single list all three hosts share. AdSessionCounter is a single; the cap is global, so more than one instance is a bug.
  • AppForegroundObserver is also a single, in its own lifecycleModule from core/lifecycle — registered in CommonAppModules.kt ahead of adsModule, since ads depend on it and not the reverse. Its Compose driver is installed once at the shell root, never per screen.
  • Developer Options → "Force ads" (F10), in feature/settings's DeveloperOptionsScreen beside the existing "Force subscription status", backed by a DeveloperFlags entry. Honoured only when isDeveloperOptionsSupported, exactly as the subscription override is. Lets placement be exercised on a Pro account, and — with a companion "reset ad session" action — makes the cap testable without waiting 30 minutes.
  • No new nav routes. Ads add no screens. The only navigation is the existing route to the subscription screen from the upsell link.

11. Testing

MockK + Truth + JUnit4 + kotlinx-coroutines-test, per the repo harness.

  • withAdSlots() — every row of PRD §6.6 (n = 0, 1, 7, 9, 10, 11, 19, 20, 25, 100), plus the group-coalescing pass and the toggled-sub-view independence.
  • AdSessionCounter — cap at 5; reserve(2) with headroom 1 grants 1; boundary resets at cold start and after ≥30 min background but not on a short background; ad_session_cap_reached fires exactly once.
  • AdSlotFormat.of() — SINGLE at COMPACT/MEDIUM, TWO_UP at EXPANDED/LARGE, and TWO_UP degrading to SINGLE at headroom 1.
  • showsAds() — false when isAdsSupported is off; false when isSubscriptionSupported is off (the inversion — worth its own named test, since it is the opposite of every sibling gate); false for PRO; true for FREE with both flags on; reacts to a status change without re-subscription.
  • Logs scroll target — scrollToLogId resolves to the same log with ads on and off, at several positions down a long list. This is the F8 regression test and the one most likely to catch a real user-visible bug.
  • Layering — a test (or a Gradle configuration assertion) that feature/ads/model and datamanager have no SDK on their compile classpath. N4 is easy to violate later and invisible when violated.

iOS bridge (Swift) — the risky onegoogleads-mobile-sdk-ios as an SPM package on iosApp; the Swift banner factory; MainEntry.installAdViewFactory + IosAdViewBridge; the UIKitView actual with the render-nothing fallback. Must be built and run on a simulator locally — CI does not build iOS, and #374 is the precedent for an unverified Swift branch shipping broken. Done when a simulator build shows a test ad and a build with no factory installed degrades to ad-free.
P9
GAStore privacy disclosures (P5 of the PRD's privacy table). Flip isAdsSupported in the release build — Android first, iOS after the P8 device validation — and only once isSubscriptionSupported is already true (PRD §13.3: ads GA cannot precede subscription GA, or free users see ads they cannot remove). Watch the §12 guardrails for two releases.
P10
Phase 2 — web on Ad ManagerOut of v1 (PRD §8.2). Blocked on the W1 account approval, which is a business task with a long lead time and should be started during P1–P4 rather than after P9. Engineering is one jsMain actual plus a web CMP.

12.1 Parallelism & critical path

P2 and P3 are independent of each other and of P1's SDK work — three people could take P2, P3 and P4 concurrently after P1. The critical path to a first real ad is P1 → P4 → P5; the critical path to GA runs through P8, which is the least verifiable phase and should not be left until last in practice even though it is numbered late. W1's account application (P10) should start immediately, since it is the only item whose duration we do not control.
